# zcall SP2.1 — Windows real-handshake capture (design)

**Date:** 2026-07-12
**Status:** design approved; pre-implementation
**Parent:** [SP2.0 — ZRTP keying gate scout](2026-07-12-zcall-sp2-zrtp-keying-gate-scout-design.md)
· [SP1 — ZRTC protocol RE](2026-07-11-zcall-sp1-zrtc-protocol-re.md)
**Reopens:** the SP2.0 verdict ([NO-GO for cheap resolution](../decisions/2026-07-12-zcall-zrtp-keying-verdict.md)) — SP2.0 was blocked only by "no machine that runs the real native engine + can capture its traffic." A **Windows** machine running real Zalo PC **is** that machine.

## Context

SP2.0 proved the keying is entirely inside the native engine: the `$zcall` JS/IPC channel on
Linux carries only high-level intent (`init`, `makeCall`→partner) — no servers/sessId/keys —
and the native engine does its own (non-Chromium) HTTP+UDP, absent on Linux. So the keying
can only be observed where the **real native engine runs**. The operator has a **Windows**
machine; Zalo PC for Windows ships `zcall_x64.node` (a PE x64 native addon) and performs the
real `call_config`/`requestcall` signaling + ZRTP UDP handshake + SRTP keying.

SP2.1 uses that machine to capture one real 1-1 call (operator's own account, calling their
own phone) and classify the keying — turning SP2.0's "can't scout cheaply" into a real
GO / NO-GO.

## Objective & scope boundary

**Objective:** capture a real call's signaling + handshake on Windows and classify the SRTP
keying into SP2.0's classes:

| Class | Meaning | Verdict |
|---|---|---|
| a | Server delivers SRTP key material (plaintext, in decrypted signaling / setConfig) | **GO** |
| b | Client derives keys from a server nonce via a standard/known KDF | **GO-ish** |
| c | Keys established in the ZRTP UDP exchange via server-attested / anti-tamper / non-standard means | **NO-GO** |

**Out of scope (YAGNI):** reimplementing the engine; static RE of the Windows binary
(deferred to a later phase only if class a/b); any media decrypt/render; anything touching
another user's account or traffic.

## Approach — tiered capture (cheapest → most reliable)

The native engine's traffic does not go through Chromium, so we capture at the OS network
level and try progressively harder TLS-decryption tiers. The primary technical unknown is
**certificate pinning** (if the engine pins, MITM fails — the UDP tier still yields framing).

1. **JS-layer instrument (try first, cheapest).** Apply this repo's diagnostics patches to
   the Windows Zalo install (same webpack bundle structure). If Windows fetches `call_config`
   at the JS/worker layer (unlike the native-only path observed on Linux), the plaintext
   config — including any server-delivered keying — is captured directly, with no Wireshark
   or TLS work. Cheap to attempt; may yield nothing if Windows is also native-only.
2. **TLS keylog (`SSLKEYLOGFILE`).** Set the env var before launching Zalo; Chromium writes
   TLS session secrets there, and Wireshark decrypts the HTTPS. Works only for traffic that
   goes through Chromium/BoringSSL and honors the var.
3. **System MITM proxy (mitmproxy + operator's own root CA).** Trust mitmproxy's CA in the
   Windows store and route traffic through it; intercepts all TLS including the native
   engine's — **unless** the engine pins certs. This is the tier most likely to expose the
   native signaling, and most likely to be defeated by pinning.
4. **UDP capture (always available).** Wireshark/Npcap captures the ZRTP/RTP **UDP** packets
   regardless of TLS. The SRTP media stays encrypted, but the ZRTP control/handshake packets'
   structure is visible — corroborating SP1 Appendix C and revealing whether keying uses a
   standard DH-style exchange (→ a/b) or an opaque server-attested one (→ c).

## What we look for (classification signals)

- **In decrypted signaling (`call_config`, `requestcall` response) or `setConfig` params:**
  SRTP key material (→ a), a KDF nonce/seed (→ b), or only session/token (keys must be in the
  UDP exchange).
- **In the ZRTP UDP handshake (via `parse-zrtppacket.js`):** a recognizable DH/ECDH or
  nonce-exchange (→ a/b feasibility) vs an opaque/attested blob (→ c).

## Components

### C1 — Windows capture runbook (`tools/zcall-re/CAPTURE-WIN.md`)

Step-by-step, assuming no Wireshark expertise: install Zalo PC Windows + log in with the
operator's account; capture filter for ZRTP/RTP UDP; set `SSLKEYLOGFILE` + point Wireshark at
it; mitmproxy + root-CA install as the fallback; the optional JS-instrument path (apply the
diagnostics patches to the Windows install); place a real 1-1 audio call to the operator's own
phone; export (a) decrypted signaling JSON, (b) the UDP packet bytes.

### C2 — Analyzer (reuse SP2.0 + SP1 tooling)

- Extend `tools/zcall-re/classify-keying.js` with `classifyFromJson(objs)` so a decrypted
  signaling capture (an array of JSON request/response bodies exported from mitmproxy or a
  keylog-decrypted session) runs through the same keying-signal classifier as the
  `[CALLDIAG-PAYLOAD]` path — no re-implementation of the signal logic.
- Reuse `tools/zcall-re/parse-zrtppacket.js` (SP1) on the captured UDP bytes to read the real
  ZRTP framing and compare against Appendix C.

### C3 — Verdict update

Rewrite `docs/superpowers/decisions/2026-07-12-zcall-zrtp-keying-verdict.md` (or add a dated
addendum) with the real Windows evidence → definitive **GO / NO-GO**, updating SP1 §E.5. If
class a/b, note that RE of `zcall_x64.node` + Linux reimplementation (SP2/SP3) is now
justified; if class c, the NO-GO is confirmed with evidence.

## Data flow

```
Zalo PC Windows (native engine)  --HTTPS-->  Zalo servers   [tier 1 JS / tier 2 keylog / tier 3 mitmproxy]
                                 --UDP ZRTP/RTP-->  media    [tier 4 Wireshark/Npcap]
```

## ToS / safety boundary (binding)

Own machine, own account, own traffic only. TLS decryption applies only to the operator's own
machine's sessions. The call is operator → operator's own phone. No third party; no decryption
of anyone else's traffic. Captures stay local; any committed sample is redacted
(`redactSecrets`) with real ids/keys/tokens replaced by placeholders.

## Testing

The analyzer additions (`classifyFromJson`, and any UDP-bytes adapter) are pure functions,
unit-tested in the style of `tools/zcall-re/__tests__/classify-keying.test.js` and
`parse-zrtppacket.test.js`. The capture itself is validated by one real run producing a
decryptable session and/or a UDP packet set.

## Success criteria

Classify the keying (a / b / c) from **real captured Windows evidence**, yielding a definitive
GO/NO-GO for the SP2–SP6 engine build. A confirmed class-c NO-GO (person-year saved, now with
hard evidence) is as valuable as a GO.
